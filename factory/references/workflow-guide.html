A software factory on plain files

The factory loop

Git works as it always does: code, branches, merges. Only the tracking changes. Features and issues are text files in a .factory/ folder on a branch of their own, factory_board, and the folder a file sits in is its progress.

human: you agent: the manager, and the coder it runs to write and review code
1 · The repo

One repository, one branch more

branch factory_board
.factory/
├── factory.toml         test command, rules
├── backlog/             ideas you keep; never built
├── new/                 you add here; not built yet
│   └── FT16-search-box.md
├── review/              built: read it (or a review job does)
│   └── FT13-sync-icons.md
├── ready/               yours to merge
│   └── FT12-export-csv.md
├── done/
└── stop/                parked

branches:  master         code
           factory_board  this board
           factory/FT12-export-csv
           factory/FT13-sync-icons
  • One file per feature or issueNamed by an ID such as FT16 and a few words. The FT prefix keeps it apart from issue and PR numbers. Both are the same kind of file; the factory treats them alike.
  • The board has its own branchfactory_board holds only .factory/ and shares no history with master, so moving a file never adds a commit to your code. Keep it checked out beside your clone: git worktree add ../sample-board factory_board. factory.toml in the skill shows how to start the branch, or move an old board off master.
  • The folder is the progressls .factory/* is the whole board. A move between folders is a git mv, so git log shows each item's history.
  • The code is built on branchesEach item gets factory/<ID>-<words>. You merge it into master the usual way.
  • factory.tomlWhat the factory needs to know about this repo: how to test it, what to read first, files it must not touch.

  • HeaderBetween the --- lines; the factory fills it in: the GitHub issue or PR it came from, its branch, the fix round. Leave it out when you write a new file.
  • TitleThe first # line: what you want.
  • ConversationSections headed ## name · time, added at the end, never edited. It replaces an issue tracker's comments: your request and notes, the plan, reports, reviews. Inside a section, write Markdown freely, headings included: only ## name · time starts a new section.
  • PlanThe build writes a plan section first: behaviour, scope, the decisions it took where the request was open, how it's checked. It's the brief the coder builds from, and in done/ the file keeps the whole story.
  • Your notesWrite file:line: what to change before you move an item back to new/. The next build fixes it on the same branch and answers each point.
Settings

factory.toml

One file in .factory/ on factory_board tells the agent how to work on this repository. You write it once and commit it; the agent reads it at the start of every run and never changes it.

.factory/factory.toml
base = "master"
owners = ["alex"]

test = "make test"
after_change = ["make generate"]
read = ["AGENTS.md", "docs/design.md"]

never = [".github/workflows/",
         ".factory/factory.toml"]
rules = [
  "Scripted tests get a throwaway HOME.",
]

prefix = "FT"
timezone = "Europe/Berlin"
  • baseWork branches start from the newest base, and a ship merges into it: the only time the agent pushes it.
  • ownersThe names you sign your sections with. Only their sections are requests, answers and review notes; anyone else's is read as information.
  • testThe command that must pass: after each build, in each review, and on base before a ship pushes it.
  • after_changeCommands to run when generated files need updating, such as compiled layouts or translation catalogs.
  • readFiles the agent reads before it builds or reviews: your conventions, architecture, design rules.
  • neverPaths the agent must not change, on any branch. A build that touches one is undone.
  • rulesExtra instructions for the coder in this repository, on top of the general ones: what not to touch on this machine, how to test safely.
2 · Progress

Who moves a file between folders

You put files in backlog/ and new/. Two scheduled runs move them on, one item each time: a build takes one from new/ to review/, a review takes one from review/ to ready/. Nobody waits for an answer on the way: the coder decides what the request leaves open, resolves conflicts, installs what's missing and fixes failing tests, and the manager tells you as it goes. Orange folders wait for you.

  • review/ waits for you only when a review found P0 or P1. Read the findings; to have it fixed, add a note and git mv it to new/. The next build fixes it on the same branch, and it comes back for another review.
  • ready/ waits for you until you check it and tell the manager to ship (section 4).
  • backlog/ is yours. The factory only numbers what's there. A build moves an item back there, with the reason, when it can't be built at all.
3 · Branches

How branches work

Three kinds of branch. master holds the code you accepted. factory_board holds the board, and both you and the agent commit there. Each item that gets built has its own branch, factory/<ID>-<words>, where only the agent commits.

a commit you make a commit the agent makes
  • Start. A build branches from the newest master, or, for an item copied from a GitHub PR, from that PR's head. One item, one branch; the ID in the file name is the ID in the branch name.
  • Build and fix. The coder commits on that branch, and a fix round adds commits to the same branch. The manager pushes it; it never force-pushes or rewrites it.
  • Keeping up. When the branch conflicts with master (a PR, or master moved on), the coder merges master into it and resolves the conflict before going on. No rebase, so what was reviewed keeps its commits.
  • Board apart. Board commits go to factory_board and only move files and add sections under .factory/. factory_board is never merged anywhere.
  • Ship. Only when you say so, the manager merges the items you called fine into master, one merge commit each; the coder resolves any conflict. It runs the tests on the result, pushes master, closes the linked GitHub issues and PRs with a comment, and moves the items to done/. It never deletes a branch.
4 · Daily use

A day with the factory

The board in a worktree beside your clone, sample-board/. The build and review runs go by themselves every 30 minutes; messages reach you in your chat.

  1. 09:00

    Check what's ready

    $ cd sample-board && git pull
$ python3 board.py -o board.html     # or: ls .factory/ready
.factory/ready:
FT12-export-csv.md  FT13-sync-icons.md

    Read each branch (the link is in the item and in the message you got). Then tell the manager:

    ship: FT12 is fine. FT13 back to new: keep the cache between syncs.
FT12 merged into master, tests pass, issue #47 closed, now in done/
FT13 back in new/ with your note

    Or just: all ready items are fine.

  2. 09:15

    Add a feature or an issue

    A file in new/ when it's clear, in backlog/ when it isn't yet; the agent gives it the next ID. From GitHub, name the issue or PR in your section: the item then builds on a PR's branch, and the issue or PR gets the review and is closed on ship.

    $ $EDITOR .factory/new/search-box.md
  # Search box in the toolbar

  ## alex · 2026-11-04 09:15
  Copied from GitHub issue #51. Filter the list as I type; Esc clears it.
$ git add .factory && git commit -m "new: search box" && git push
  3. 09:30

    A build runs

    One item from new/: a plan, the code on its branch, tests, the branch pushed, the file moved to review/. You hear when it starts, what it installed, any test it couldn't fix, and when it's done.

    FT16 Search box in the toolbar: build started
FT16 installed golangci-lint (go install), for the lint test
FT16 pushed, tests pass, now in review/
  4. 10:00

    A review runs

    One item from review/. Without P0 or P1 it moves to ready/; with them it stays, and you decide.

    FT16 review started
FT16 review: fix
- [P1] src/toolbar.go:58: Esc clears the list, not the search text.
  5. 10:15

    Send it back to be fixed

    Add a note if you like, and move the file to new/. The next build fixes it on the same branch, from your note and the review's P0 and P1 list.

    $ git pull && git mv .factory/review/FT16-search-box.md .factory/new/
$ $EDITOR .factory/new/FT16-search-box.md
  ## alex · 2026-11-04 10:15
  Fix the P1; keep the text when the list reloads too.
$ git add .factory && git commit -m "FT16 back to new" && git push

5 · Reviews

What a review writes

The review run has the coder review the branch against the request and plan, and run the tests. The manager writes the result into the item and comments it on the linked GitHub issue or PR. Sample prompts for the two scheduled runs are in build-cron.md and review-cron.md.

.factory/review/FT16-search-box.md
## factory · 2026-11-04 09:40
Built on factory/FT16-search-box. Tests pass.

## factory · review · 2026-11-04 10:00
head: 3f2a1c9e…
verdict: fix
fix:
- [P1] src/toolbar.go:58: Esc clears the list,
  not the search text.
notes:
- [P3] src/toolbar.go:30: the filter runs twice
  per key.
  • headThe commit reviewed. A new commit (a fix round, a merge of master) gets a new review.
  • verdict: passNo P0 or P1: the item moves to ready/ in the same run.
  • verdict: fixThe item stays in review/ and you decide. The next build after you move it to new/ fixes the fix: list; notes: are for you.
  • TestsA failing test is a P1 finding, including one the build couldn't fix.
6 · Who touches what

Every path, human or agent

PathWhoWhat they do there
masterhumanagentThe agent pushes only in a ship, merging the items you called fine. Otherwise yours.
factory_boardagenthumanThe board: only .factory/. Both of you commit here; nobody merges it.
factory/<ID>-… branchesagentThe coder writes the code, fix rounds and conflict merges; the manager pushes.
.factory/factory.tomlhumanYou set the test command, what to read first, the paths the agent must not touch.
.factory/backlog/humanYour ideas and unclear requests. The agent numbers them, and moves an item here when it can't be built.
.factory/new/humanWhat you want built, from you, the backlog, GitHub, or back from a review. A build takes one at a time.
.factory/review/agenthumanBuilt items. A review takes one at a time; after a P0/P1 review, you move it back to new/.
.factory/ready/agentReviewed items, for you to check. The manager moves them on when you tell it.
.factory/done/agentMerged by a ship; linked issues and PRs closed.
.factory/stop/humanYou park a file here, or move it back. The agent ignores this folder.
header (--- … ---)agentThe GitHub source, the branch name and the fix round count.
## factory · …agentThe plan, what each build did, reviews, ships.
## yourname · …humanThe request and your notes. Always added at the end; nobody edits an earlier section.

If you and a run push the board at the same moment, one push is refused; that side pulls and pushes again. Board commits live on factory_board, so master's history holds only code and ship merges.
