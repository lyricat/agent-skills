A software factory on plain files

The factory loop

Git works as it always does: code, branches, merges. Only the tracking changes. Features and issues are text files in a .factory/ folder of the repo, and the folder a file sits in is its progress.

human: you agent: the factory pass, and Claude Code it runs to write code

  • One file per feature or issueNamed by an ID such as FT16 and a few words. The FT prefix keeps it apart from issue and PR numbers. Both are the same kind of file; the factory treats them alike.
  • The folder is the progressls .factory/* is the whole board. A move between folders is a git mv, so git log shows each item's history.
  • The code is built on branchesEach item gets factory/<ID>-<words>. You merge it into master the usual way.
  • factory.tomlWhat the factory needs to know about this repo: how to test it, what to read first, files it must not touch.

  • HeaderBetween the --- lines; the factory fills it in. You can leave it out when you write a new file.
  • TitleThe first # line: what you want.
  • ConversationSections headed ## name · time, added at the end, never edited. It replaces an issue tracker's comments: questions, answers, review notes. A question section from the factory means the item waits for your answer, in whatever folder it is. Inside a section, write Markdown freely, headings included: only ## name · time starts a new section.
  • PlanOnce the item is clear, the factory writes a plan section: behaviour, scope, decisions, how it's checked. It's the brief Claude Code builds from, and in done/ the file keeps the whole story.
  • Review notesWrite file:line: what to change. The next pass fixes it on the same branch and answers each point.
Settings

factory.toml

One file in .factory/ tells the agent how to work on this repository. You write it once and commit it; the agent reads it at the start of every pass and never changes it.

.factory/factory.toml
base = "master"
remote = "origin"
owners = ["alex"]

test = "make test"
after_change = ["make generate"]
read = ["AGENTS.md", "docs/design.md"]

never = [".github/workflows/",
         ".factory/factory.toml"]
rules = [
  "Scripted tests get a throwaway HOME.",
]

review = false
max_rounds = 3
notify = "notify-send -a factory {title} {text}"
  • base, remoteThe branch you merge into and the remote everything is pushed to. Work branches start from the newest base; board commits go onto it.
  • ownersThe names you sign your sections with. Only their sections are requests, answers and review notes; anyone else's is read as information.
  • testThe command that must pass before an item reaches ready/. The agent runs it after every build and fix round.
  • after_changeCommands to run when generated files need updating, such as compiled layouts or translation catalogs.
  • readFiles the agent reads before it analyses a request or builds it: your conventions, architecture, design rules.
  • neverPaths the agent must not change, on any branch. A build that touches one is undone.
  • rulesExtra instructions for Claude Code in this repository, on top of the general ones: what not to touch on this machine, how to test safely.
  • reviewSet it to true when a review job reviews each build. A built item then waits in review/ until its latest commit has a review without P0 or P1 findings; a review with them starts a fix round.
  • max_roundsFix rounds on one item before the agent stops and asks you, listing what's left.
  • notifyRun when an item reaches ready/; {title} and {text} are filled in. Leave it out to get the news only in the pass's summary.
2 · Progress

Who moves a file between folders

The factory moves every file except to add, park or resume one. A question never moves a file: it waits where it is until you answer. Orange folders wait for you.

3 · Branches

How branches work

Two kinds of branch. master holds the code you accepted and the board. Each item that gets built has its own branch, factory/<ID>-<words>, where only the agent commits.

a commit you make a commit the agent makes
  • Start. When an item becomes clear, the agent branches from the newest master. One item, one branch; the ID in the file name is the ID in the branch name.
  • Build and fix. Claude Code commits the code on that branch, and every fix round adds commits to the same branch. The agent pushes it; it never force-pushes or rewrites it.
  • Keeping up. When master moves on and the branch no longer merges cleanly, the agent merges master into the branch and runs the tests again. It doesn't rebase, so what you already reviewed keeps its commits.
  • Board on master. The agent's commits on master only move files and add sections under .factory/. It never puts code on master.
  • Finish. You merge the branch into master. For a file in ready/, the next pass sees the merge and moves it to done/; otherwise, or after a squash or rebase merge, move it yourself. However a file reaches done/, the next pass where gh works closes what it links: the issues and PRs your sections name with Closes #12, Fixes #12 or Resolves #12, the issue or PR the item builds, and the branch's open PRs. It notes what it closed in a last section, once. Deleting the branch is yours too; the agent never deletes a branch.
4 · Daily use

A day with the factory

All in your usual clone of sample-project/. A pass runs by itself every 30 minutes.

  1. 09:00

    See what waits for you

    $ git pull
$ python3 board.py -o board.html     # or: ls .factory/review .factory/ready
.factory/review:
.factory/ready:
FT12-export-csv.md
  2. 09:05

    Merge what's ready

    Read the branch and merge it. The next pass moves the file to done/.

    $ git diff master...origin/factory/FT12-export-csv
$ git merge origin/factory/FT12-export-csv && git push
  3. 09:15

    Add a feature or an issue

    A new file in new/, named by a few words; the agent gives it the next ID, so two people adding at once never clash. Write it as you'd tell a colleague.

    $ $EDITOR .factory/new/search-box.md
  # Search box in the toolbar

  ## alex · 2026-11-04 09:15
  Filter the list as I type; Esc clears it.
$ git add .factory && git commit -m "new: search box" && git push
  4. 09:30

    A pass runs

    It reads FT16, finds one unclear point, writes a question section at the end of the file and pushes. The file stays in new/ and waits for you.

    FT16 search-box   new/   1 question
  5. 10:00

    Answer the question

    Add your section at the end and push. Leave the file where it is.

    $ git pull && $EDITOR .factory/new/FT16-search-box.md
  ## alex · 2026-11-04 10:00
  Yes, case-insensitive.
$ git commit -am "answer: FT16" && git push
  6. 10:30

    The next pass builds it

    A plan section in the item file, the code on factory/FT16-search-box, tests run, branch pushed, file moved to review/, and a notification for you.

    FT16 search-box   new/ → review/   branch factory/FT16-search-box
  7. 14:00

    Review: accept, or ask for a change

    With a review job (section 5), it reviews first and only clean builds reach ready/; you can still add notes of your own. Without one, read the branch. Good: merge it, and git mv the file to done/ yourself, since only files in ready/ move there on their own. Not yet: write what to change, and the next pass fixes it on the same branch.

    $ git fetch && git diff master...origin/factory/FT16-search-box
$ $EDITOR .factory/review/FT16-search-box.md
  ## alex · 2026-11-04 14:00
  src/toolbar.go:41: keep the text when the list reloads.
$ git commit -am "review: FT16" && git push

5 · Optional review job

Review before ready/

With review = true in factory.toml, a second scheduled job reviews every build, and the factory waits for it. An item reaches ready/ only when its latest commit has a review without P0 or P1 findings and the tests pass merged with master. Sample prompts for the job are in review-cron.md (in a clone) and review-cron.gh.md (through gh).

.factory/review/FT16-search-box.md
## factory · 2026-11-04 10:30
Built on factory/FT16-search-box. Tests pass.

## reviewer · review · 2026-11-04 11:00
head: 3f2a1c9e…
verdict: fix
fix:
- [P1] src/toolbar.go:58: Esc clears the list,
  not the search text.
notes:
- [P3] src/toolbar.go:30: the filter runs twice
  per key.

## factory · 2026-11-04 11:30
Round 1: Esc clears the text (toolbar.go:58).

## reviewer · review · 2026-11-04 12:00
head: 8b07d24a…
verdict: pass
  • headThe commit the review is about. It counts only while that is still the branch's latest commit; a fix round or a merge of master needs a new review.
  • verdict: passNo P0 or P1. The next pass tests the merge and moves the item to ready/.
  • verdict: fixThe next pass makes a fix round from the fix: list only; notes: are for you. Review rounds count toward max_rounds.
  • WaitingUntil its latest commit is reviewed, an item stays in review/ and passes leave it alone.
  • SetupPut the job's git name in owners. Your own notes still work as before, and a review never answers a question meant for you.
6 · Who touches what

Every path, human or agent

PathWhoWhat they do there
src/ … on masterhumanChanges only by your merges. The agent never commits code to master.
factory/<ID>-… branchesagentClaude Code writes the code and fix rounds; the agent pushes, and merges master in when needed. You read them and merge them.
.factory/factory.tomlhumanYou set the test command, what to read first, the paths the agent must not touch.
.factory/new/humanYou create files here. The agent asks its questions in them and moves them on once built; you answer in the file.
.factory/review/agenthumanThe agent puts a built item here; you, or the review job, read the branch and write review notes in the file.
.factory/ready/agenthumanThe agent puts a finished item here; you merge its branch.
.factory/done/agenthumanThe agent moves a file here from ready/ once its branch is merged, and never reads it again. You move the rest: items merged from review/, or by squash or rebase.
.factory/stop/humanYou park a file here, or move it back to new/. The agent ignores this folder.
header (--- … ---)agentThe branch name and the fix round count.
## factory · …agentQuestions, the plan, what each build and fix round did.
## yourname · …humanThe request, answers, review notes. Always added at the end; nobody edits an earlier section.
## reviewer · review · …agentThe review job, signed with a name in owners: the commit it reviewed, the verdict, P0/P1 findings to fix and other notes.

If you and a pass push at the same moment, one push is refused; that side pulls and pushes again, as with any two people sharing a branch. A board commit touches only .factory/, so CI can skip it, and git log -- src leaves it out.
